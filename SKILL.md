# Renaissance Rococo Web Design

Create expressive websites in which historical image-making and modern web behavior reinforce each other. The result may be ornate, dramatic, quiet, or restrained, but it must be materially convincing, readable, and specific to the content.

This is an original design methodology informed by art-history and interface research. It is not an official design system of Gucci, Claude, Shopify, or any museum.

## Route the request

- **Research or direction:** inspect references and produce a sourced visual system. Do not generate or implement unless requested.
- **Concept or preview:** define the whole visitor path, then make the smallest artifact that tests the risky relationship.
- **Implementation:** build reusable scene, material-boundary, collection, article, and artwork components around semantic HTML.
- **Critique:** inspect the actual artifact at relevant states and viewports; identify concrete failures in composition, material, continuity, reading, interaction, and performance.

The latest user request determines the stage. A prior request to pause design does not permanently prevent later authorized design work.

## Essential design contract

1. **Design the whole journey.** Treat the entrance, collection, detail opening, article middle, artwork view, and return path as one system. A beautiful hero alone does not establish the direction.
2. **Use a normal desktop webpage.** Start with 1440×900 and 1920×1080 CSS viewports, then test low-height laptops and responsive fallback. Do not present a portrait poster inside browser chrome as a desktop design.
3. **Let richness come from relationships.** Use scale, crop, perspective, gaze, overlap, color, and material handoff before adding ornamental frames.
4. **Keep long-form text as web text.** Navigation, articles, quotes, footnotes, and formulas remain selectable, zoomable, searchable, and adaptable. A PDF may be a download, not the primary reading surface.
5. **Make ornament specific.** Rococo may contribute asymmetric curves, botanical or marine growth, invention, and local intricacy. It does not require symmetrical gold borders, parchment rods, beige aging, or palace props.
6. **Separate originals from reinterpretations.** Preserve artworks and identity-sensitive images in their authoritative view. Decorative crops or collage fragments must not masquerade as the original.
7. **Use motion to explain passage.** Motion may enter a space, reveal an entrance, cross a material boundary, or locate an object. It must be interruptible and have a reduced-motion path.

## Observe before composing

Classify each input as an original to preserve, a supporting insert, a style reference, or a rejected anti-reference. Record what is visibly true: subject, scale, axes, depth, visual weight, edge material, text role, movement, and source limits.

Separate three layers in the reasoning:

- **Observed:** visible in the source or stated by an authoritative reference.
- **Inferred:** an interpretation of why the source feels a certain way.
- **Decided:** a project-specific choice with a page role and verification method.

Build from one primary spatial mechanism and one primary material mechanism per scene. Secondary languages support them; they do not receive equal visual weight.

## Design and build

1. Identify the page's real content and visitor task.
2. Choose one memorable visual event and define the quiet regions that make it legible.
3. Define cross-page invariants: type roles, reading surface, chapter identity, navigation behavior, image-crop language, and material handoff.
4. Define both a high-expression state and a long-reading state, plus the exact element that survives between them.
5. Build semantic content first. Attach scenery and animation as progressively enhanced layers.
6. Test the complete path: entrance → collection → detail → article middle or artwork view → return.

Do not call a proposal “refined,” “luxurious,” or “cohesive” without naming the visible mechanism that creates that result.

## Deliver

- For research, provide sources, observations, transferable mechanisms, exclusions, and uncertainties.
- For design, provide the actual preview and state what it does and cannot prove.
- For implementation, provide the runnable result, tested environments, failures corrected, and remaining limitations.

Do not claim browser compatibility from a static image or motion quality from a written specification.
